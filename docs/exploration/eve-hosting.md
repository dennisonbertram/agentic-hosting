# Hosting Eve agents on agentic.hosting

## Eve's self-hosted contract

Eve is a TypeScript agent framework that produces a Nitro Node server. Its current getting-started guide requires Node.js 24 or newer and a model-provider credential. For self-hosting, Eve documents `eve build` followed by `PORT=3000 eve start --host 0.0.0.0`; the output is a long-running service, with TLS, process restarts, and logs managed by the host. [Getting started](https://eve.dev/docs/getting-started) · [Self-hosting](https://eve.dev/docs/guides/deployment/self-hosting)

The platform already has a generic Git/Nixpacks build path and per-service port configuration. The installer pins Nixpacks 1.41.0, whose upstream Node provider lists Node 24; Eve apps should declare Node 24 in `package.json` and use scripts for the Eve build and start commands. The current app image must listen on the configured service port. The build flow is in `internal/builder/builder.go`, service container settings are in `internal/docker/client.go`, and host-based Traefik route generation is in `internal/services/services.go`. This is a source-level compatibility assessment, not a successful Eve deployment test. [Nixpacks 1.41.0 Node provider](https://github.com/railwayapp/nixpacks/blob/v1.41.0/src/providers/node/mod.rs)

Eve's workflow state is durable only when its selected Workflow world has durable storage. The default self-hosted local world writes `.eve/.workflow-data`, which Eve says must be mounted to persistent storage to survive container replacement. This platform currently starts tenant services with a read-only root filesystem and no persistent service volume, so that default is not supported across redeploys. Eve also supports a pluggable Workflow world, but its Postgres reference package must match Eve's `@workflow/*` protocol version. The package documentation describes its Postgres implementation as a reference, not optimized for security, and says workflow routes require protection. [Eve persistence guidance](https://eve.dev/docs/guides/deployment/self-hosting) · [Postgres World](https://workflow-sdk.dev/worlds/postgres)

## Platform compatibility and gaps

- **Runtime and build:** Node 24 is available in the pinned Nixpacks provider. A project can provide `build` and `start` scripts that call Eve's documented commands. The service runtime currently does not add Eve-specific lifecycle behavior.
- **Ingress:** Each service receives a whole-host Traefik route, so it can preserve `/eve/` and `/.well-known/workflow/` without rewriting paths. Eve requires both prefixes. The current live service smoke is failing at Traefik-to-tenant connectivity (`HTTP 502`, with the tenant network drop counter increasing); ingress compatibility has not yet passed end to end. [Eve proxy requirements](https://eve.dev/docs/guides/deployment/self-hosting)
- **Workflow callback security:** The Postgres World receives orchestration on `POST /.well-known/workflow/v1/flow`. Its official documentation says this route has no built-in caller authentication and recommends blocking it at the ingress when its worker calls a loopback address. The platform currently routes the whole service host to the app and does not yet offer a service route rule to block only this path. Do not expose an Eve app using this World publicly until this route restriction and any public webhook paths are tested together. [Postgres World security](https://workflow-sdk.dev/worlds/postgres#security)
- **Model and tool network access:** Tenant networks are configured as internal networks without outbound internet access. Eve requires an external model credential/provider, so ordinary provider calls will not work under that restriction. The runtime needs a deliberately scoped egress path that preserves tenant isolation and handles user-supplied credentials safely.
- **Sandbox:** Eve separates its trusted Node runtime from a per-session filesystem/process sandbox. Its self-hosting guide says the default provider selects Docker, microsandbox, or just-bash based on availability. Tenant services have no Docker socket, run under gVisor, and have read-only roots; the platform should not expose the host Docker socket to make Eve's default Docker sandbox work. A compatible explicit sandbox backend and its filesystem/network lifecycle need to be selected and tested. [Eve sandbox model](https://eve.dev/docs/concepts/execution-model-and-durability) · [Sandbox setup](https://eve.dev/docs/sandbox)
- **Authentication:** Eve's session/channel routes fail closed in production unless the application configures a real authenticator; development-only auth is not a production policy. Route auth does not replace protection of the Workflow callback route. Platform tenant API keys are deployment credentials and are not automatically forwarded as app authentication. [Eve authentication](https://eve.dev/docs/guides/auth-and-route-protection)
- **Versioning:** For non-Vercel Workflow worlds, Eve documents one Eve version per world at a time. Sessions can become stranded after a version change. Pin the Eve version and do not run overlapping old/new replicas against the same world without an Eve-supported migration/routing strategy. [Eve execution and durability](https://eve.dev/docs/concepts/execution-model-and-durability)

The current restore smoke also has separate platform blockers: environment execution returned exit codes 0 and 7 under runsc, but service ingress still returns 502 and managed database provisioning is blocked by missing database images. Those results do not establish Eve compatibility.

## Smallest future support path

Start with one pinned Eve app running as a normal service, using Node 24, Eve's documented build/start commands, a configured application authenticator, and a supported sandbox provider. Before calling this full support, the platform needs and must validate: (1) a persistent per-service mount for `.eve/.workflow-data` or a version-matched Workflow world; (2) scoped outbound model access; (3) a way to keep `/.well-known/workflow/v1/flow` private while preserving Eve routes and any intentional webhooks; and (4) a secure sandbox backend that does not grant the app host Docker control. Test a real model turn, a streamed response, callback delivery, restart/redeploy recovery, denied unauthenticated session requests, denied external flow-route access, and sandbox isolation. The current shared service-routing failure and missing database images must be resolved before that runtime test can be run here.

This note records an integration assessment only. No Eve app, package, credential, route, or infrastructure change has been made, and Eve has not been deployed on this platform.
